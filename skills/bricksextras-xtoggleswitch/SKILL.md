# BricksExtras: Toggle Switch (xtoggleswitch)

Shipped by the **BricksExtras** plugin. Not nestable — all internal markup is generated by the element itself from settings, unlike a plain Bricks container. Typically pairs with an **`xcontentswitcher`** elsewhere on the page, which it drives.


**Before building from any template below, read this element's schema JSON now — do this even if you haven't loaded `bricksextras-start-here` or `bricksextras-element-schemas` this session:** open `references/elements/xtoggleswitch.json` inside the `bricksextras-element-schemas` skill directory and read it. If that file is missing, or its `schemaVersion` doesn't match the live BricksExtras plugin version, fall back to whatever live schema ability the current MCP connection exposes (e.g. `bricks/get-element-schema` on the native Bricks MCP) for `xtoggleswitch` instead. The templates and examples below show documented required structure and common patterns only — the schema file (or live call) is the source of truth for the complete, current set of available settings. Do not proceed to write settings JSON until you've actually opened one of these two sources this session.

## `type: "double"` vs `type: "multiple"` are genuinely different elements sharing one name

They render entirely different DOM (see "Rendered structure" below) and their style/behavior controls barely overlap — most controls are `required` on one `type` or the other, not both.

- **`double`** — a classic two-label switch (e.g. "Monthly" / "Yearly"). The actual interactive control is a pair of visually-hidden native radio inputs, not the visible slider div. Style with `leftLabel`/`rightLabel`, `sliderWidth`/`sliderBackgroundColor`/`controlSize`, etc. (all `required: ["type","!=","multiple"]`).
- **`multiple`** — a row of labeled tab-like buttons with a JS-positioned active-state highlight, behaving like a tab list (`role="tablist"`, each label is a `role="tab"` button). Style with `labelActiveBackgroundColor`, `labelActiveTypography`, etc. (all `required: ["type","=","multiple"]`). This is the mode to use for "one label per post" query-loop builds.

## `multiple` mode: driving labels from a query loop

Set `hasLoop: true` + a `query` object + `labelsQuery` (a plain text/dynamic-tag field, e.g. `"{post_title}"`).

**This JSON is an example, not the schema.** Before copying settings out of this block, read `references/elements/xtoggleswitch.json` in `bricksextras-element-schemas` (live schema ability as fallback if missing/stale) and confirm they still exist and mean what's shown here.

```json
{
  "name": "xtoggleswitch",
  "settings": {
    "type": "multiple",
    "hasLoop": true,
    "query": { "objectType": "post", "post_type": ["post"], "posts_per_page": 6 },
    "labelsQuery": "{post_title}",
    "whichSwitcher": "selector",
    "switcherSelector": ".post-content-switcher"
  }
}
```

**Do not add the `labels` repeater when `hasLoop` is true** — it's not needed, `labelsQuery` fully replaces it in loop mode (fixed in plugin PHP; earlier versions required a populated `labels` array even in loop mode due to a guard-clause ordering bug — if debugging on an older BricksExtras version and the element renders nothing, check for that).

**Pairing with `xcontentswitcher`**: give the switcher a class (e.g. `post-content-switcher`) and point `switcherSelector` at it — same class-based targeting convention as everywhere else in BricksExtras (see `bricksextras-start-here`'s "Targeting another element"). The switcher's own looping child block needs an **identical** `query` object to the toggle's, so label index N and panel index N stay aligned — same query-index-alignment trick used for slider/tabs/accordion query loops. **Avoid `orderby: rand` (or similar random ordering) on this pairing** — the toggle and switcher run their queries independently, so a stable default order is what keeps label index N and panel index N aligned.

## One toggle can drive multiple switchers at once — and switchers don't need to be full tab panels

`switcherSelector` is a plain CSS class selector, and BricksExtras' switching JS applies it to **every** matching `xcontentswitcher` on the page, not just the first one found — a single `xtoggleswitch` can synchronize several independent switcher instances simultaneously as long as they all carry the same class.

This matters because it unlocks a layout that isn't the obvious "tabs" shape: instead of one big `xcontentswitcher` whose panels duplicate an entire block per option, use several small `xcontentswitcher` instances — each wrapping only the one or two elements that actually change — scattered inside an otherwise static structure, all pointed at the same `switcherSelector`. A pricing block can have a shared heading, a shared "Pricing" label, and shared Terms & Conditions text that never re-render, while only the feature list and the price/CTA are individually wrapped in their own tiny switcher and swap together. See `bricksextras-xcontentswitcher`'s "Granular pattern" section for the full example.

This is distinct from the `componentScope`/multi-instance-collision problem described in `bricksextras-start-here`'s "Targeting another element" — that warning is about a **class matching more elements than intended** across duplicated component instances (an accidental collision). Here, matching multiple elements is the whole point, and it's a plain page-level class, not something living inside a duplicated component — so the collision risk doesn't apply. If the same pattern is built *inside* a component that gets instanced more than once, the usual component-scope caution still applies.

## Rendered structure — schema alone doesn't show this

The `css` array on each style control tells you *which selector* it targets, but not the surrounding structure, which parts are JS-managed at runtime vs static, or which parts are the real interactive element. Useful when writing `_cssCustom` or `_interactions` beyond what native controls cover.

### `multiple` mode

```html
<div class="brxe-xtoggleswitch x-toggle-switch" data-x-switch='{"type":"multiple","contentSwitcher":".post-content-switcher"}'>
  <div class="x-toggle-switch_labels" role="tablist" aria-label="Switch content">
    <button class="x-toggle-switch_label x-toggle-switch_label-active" role="tab" aria-selected="true" tabindex="0" aria-controls="{switcher-id}_0">
      <span>Post A</span>
    </button>
    <button class="x-toggle-switch_label" role="tab" aria-selected="false" tabindex="-1" aria-controls="{switcher-id}_1">
      <span>Post B</span>
    </button>
    <!-- ...one button per loop item... -->
    <div class="x-toggle-switch_multiple-slider" style="left: 5px; width: 75px; height: 48px; top: 5px;"></div>
  </div>
</div>
```

- **`.x-toggle-switch_multiple-slider` is JS-positioned, not CSS-laid-out** — its `left`/`width`/`height`/`top` are inline px values computed at runtime from the active button's measured bounding box. Custom CSS that changes label padding/font-size/gap can desync this highlight from the visible label unless the JS re-measures on the triggering change. Test after any layout-affecting custom style, don't assume it self-corrects.
- Every tab button carries a working `aria-controls` pointing at the paired content-switcher panel — real accessibility wiring, not decorative.

### `double` mode

```html
<div class="brxe-xtoggleswitch x-toggle-switch" data-x-switch='{"type":"double","contentSwitcher":".post-content-switcher"}'>
  <span class="x-toggle-switch_label">Monthly</span>
  <div class="x-toggle-switch_switch">
    <span class="x-toggle-switch_slider">
      <span class="x-toggle-switch_control"></span>
    </span>
    <fieldset class="x-screen-reader screen-reader-text">
      <legend class="x-screen-reader">Switch pricing</legend>
      <input class="x-toggle-switch_left-input" type="radio" name="x-toggle-switch_{id}" checked>
      <label class="x-screen-reader">Monthly</label>
      <input class="x-toggle-switch_right-input" type="radio" name="x-toggle-switch_{id}">
      <label class="x-screen-reader">Yearly</label>
    </fieldset>
  </div>
  <span class="x-toggle-switch_label">Yearly</span>
</div>
```

- **The real interactive control is the pair of radio inputs inside the visually-hidden fieldset**, not the visible `.x-toggle-switch_switch`/`.x-toggle-switch_slider` div that looks clickable. If wiring custom `_interactions` or JS against "the switch," target the radios (`.x-toggle-switch_left-input`/`.x-toggle-switch_right-input`) or their labels, not the visible slider div.
- The left/right `.x-toggle-switch_label` spans are plain `<span>`, not buttons — no tab semantics, unlike `multiple` mode's labels.

## Never do

- Do not add a static `labels` repeater array alongside `hasLoop: true` expecting it to combine with `labelsQuery` — `labelsQuery` fully replaces it in loop mode.
- Do not target `.x-toggle-switch_switch` for interactions expecting it to behave like the real toggle control in `double` mode — the actual state lives on the hidden radio inputs.
- Do not assume `.x-toggle-switch_multiple-slider`'s position is CSS-driven — it's computed inline by JS from real measurements; verify after custom layout changes rather than assuming it adapts.
- Do not reuse style controls across `type` values — `double`-only and `multiple`-only controls are structurally inapplicable to the other mode, not just hidden in the builder UI.

## MCP write notes

- When pairing with a query-looped `xcontentswitcher`, keep both `query` objects byte-for-byte identical (same `post_type`, `posts_per_page`, ordering) to keep label/panel indices aligned.
